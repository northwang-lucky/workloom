== active skill boundaries/steps
3:description: Design or complete case.md for an active, planning, or in_progress full task, then execute it after implementation is ready. Use when the user asks to add, rebuild, review, batch-confirm, or execute CASE artifacts for non-archived tasks; also use for legacy in_progress tasks without a case record. Do not use for light, completed, or archived tasks.
4:whenToUse: Use on planning/in_progress full tasks that need CASE design, completion, confirmation, execution, or batch processing; route archived work to workloom-case-archived instead.
9:Supplement CASE artifacts for non-archived full tasks without replacing the normal workflow. The main session orchestrates; a check executor designs and executes CASE. Keep one active task at a time and preserve the user's confirmed caseHash.
13:- Accept only `planning` or `in_progress` tasks with `mode: "full"`.
14:- Reject tasks with `mode: "light"`; they keep their normal self-check. A completed task under `tasks/archive/` belongs to `workloom-case-archived`; reject it here.
15:- A planning task still authors and reviews plan.md through Phase 1.4. If legacy design.md + implement.md exist without plan.md, load `workloom-migrate-plan` first and re-confirm any stale PRD credential. If only PRD exists, stop and return to normal planning; do not invent a PLAN inside this skill.
21:1. With an active task, inspect that task. With no active task, call `workloom_task_list` for planning and in_progress, then inspect each full task. Exclude completed/archive/light tasks. Order candidates by `createdAt`, then task path.
27:1. Reuse an existing passed result only when all of these hold: `case.required=true`; the current case.md hash equals `case.caseHash`; the RESULT's caseHash matches it; `case.result.resultHash` equals the current case-result.md hash; check is recorded; and the RESULT codeBaseline contains `codeFingerprint=<64-hex>` equal to the current fingerprint. Compute the current RESULT hash with `node --input-type=module -e "import { readFileSync } from 'node:fs'; import { computeCaseHash } from '@workloom-ai/core'; console.log(computeCaseHash(readFileSync('<case-result-path>', 'utf8')))"`, which uses the same CRLF/CR→LF plus SHA-256 rule as core. Run this from the workloom repository root (or another directory where `@workloom-ai/core` resolves), passing an absolute case-result path when the target is elsewhere. Return the existing evidence and do not create a new session.
28:2. Otherwise dispatch `workloom_execute` with `kind: check`, `purpose: case-design`, a semantic title, and a prompt to create or revise case.md from the current PRD, PLAN, real code, and canonical assets. Never pass model or effort on a continuation.
29:3. If `case.designSession` exists, continue that session with `kind: check` and `purpose: case-design` for review revisions. If it is absent, start the design dispatch and record the resulting child id. For an old task with `case: null`, the design dispatch may create a non-required case record; confirm must promote it to `required: true`.
35:2. Continue the same design session with `kind: check`, `purpose: case-design`, and concrete changes for every problem. Re-run review until `readyToConfirm=true`.
37:4. The original design/confirm/execute request or a generic "continue" is never an approval. After every review, stop and wait for a new user message that explicitly approves the current caseHash. The same rule covers batches.
43:1. Planning tasks and in_progress tasks whose implementation is still running stop after CASE confirmation. Leave the task in its current status and create no execution result.
45:3. For a ready task, continue `case.designSession` with `kind: check`, `purpose: execution`, and the confirmed caseHash. The check executor completes every SR item, then C1 through Cn in order, collects real coverage, and writes case-result.md, case-evidence/, and coverage/ without changing the confirmed CASE.
47:5. P2 fixes follow the existing check discipline and trigger a full SR/C/coverage rerun. Report P0/P1 to the main session. Never force a core CASE failure.
53:3. For a batch, process tasks serially in the confirmed order and update the batch file after each execution. On the first P0/P1 or blocked result, stop later execution and report completed, failed, and untouched tasks.
