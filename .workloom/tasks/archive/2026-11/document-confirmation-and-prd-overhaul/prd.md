# 简化人工确认并升级需求与计划文档规范

## Context

workloom 的原有流程要求用户在多个文档上反复确认，并把文档哈希和 CASE 授权暴露给用户。PLAN 又要求提前写出完整代码，PRD 则容易退化为对齐问答的记录。

本次容器任务组织三个顺序子任务，分别处理确认流程、PLAN 编写和 PRD 结构。容器本身不再新增实现，只负责检查三个子任务是否完整交付。

## Goal

最终流程只保留必要的人工内容确认。PRD 与 PLAN 分阶段确认，CASE 由主会话复核后直接使用。

PLAN 使用带输入、输出、前置条件、处理过程和失败路径的伪代码。PRD 使用结构完整且叙述连贯的需求格式，不再依赖开放节点 HTML 标记，也不按问答过程记账。

## Scope

### In scope

验收三个子任务的提交、检查、CASE、归档和会话记录，并确认主仓库包含它们的最终修改。

### Non-goals

容器不新增生产代码，不重复执行所有子任务的详细实现，不修改任何已归档内容。

## Assumptions, Constraints and Dependencies

三个子任务按确认流程、PLAN、PRD 的顺序执行。后续任务依赖前一任务的输出，因此验收以各自归档时的实际结果为准。

当前宿主在子任务执行期间仍加载旧版工具。为完成过渡，部分任务记录保留了旧运行时兼容字段；这些字段不属于目标实现。

## Requirements

### 子任务交付

- R1：人工确认流程子任务必须完成内容确认简化、哈希机制移除和 CASE 主会话复核执行。
- R2：PLAN 规范子任务必须完成五字段伪代码协议及其结构检查。
- R3：PRD 格式子任务必须完成业界结构融合、反流水账规则和开放节点标记移除。

### 容器验收

- R4：三个子任务必须全部归档为 completed，具有通过检查和有效 CASE 结果，主仓库必须包含对应工作提交。

## Acceptance Criteria

- AC1（覆盖 R1、R2、R3、R4）：逐项读取三个子任务的归档记录，确认状态、检查摘要、CASE 结果和工作提交完整。验证方法是运行容器 CASE 的归档与结果检查。
- AC2（覆盖 R4）：主仓库历史包含三个工作提交，且归档顺序与子任务执行顺序一致。验证方法是运行 git 历史与任务记录检查。
- AC3（覆盖 R4）：三个子任务的最终验证记录均为通过，Open issues 均为 none，容器没有新增未提交实现文件。验证方法是运行结果文件与工作区检查。

## Edge Cases and Failure Paths

任一子任务未归档、检查失败或结果文件无效时，容器不得归档。只存在旧宿主兼容字段不构成失败，因为它不代表目标流程仍要求用户确认 CASE。

## Risks and Open Questions

没有剩余开放问题。主要风险是只看子会话自述而遗漏真实结果，因此容器验收必须读取归档记录和结果文件。

## Alignment Decisions

容器保持无自身 PLAN 的既有豁免，不重复创建实现计划。验收依据三个子任务的实际交付物，而不是重新组织需求或追加实现。
