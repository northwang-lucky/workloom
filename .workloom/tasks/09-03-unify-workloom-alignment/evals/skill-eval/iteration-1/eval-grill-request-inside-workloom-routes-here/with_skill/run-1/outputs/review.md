## 这轮怎么压

我会按 design tree 的固定根节点顺序推进，每一轮把当前 frontier（前置条件已确定、现在就能问的所有节点）合并成一个编号批次一次性抛出，答完一轮再重算 frontier，直到没有开放节点：

1. **目标与价值** — 需求的"完成"长什么样，为什么值得做。
2. **范围与非目标** — 明确什么不做。
3. **环境约束** — 平台、依赖、规范、运行时。
4. **可观测验收标准** — 旁观者如何判断 done / not-done。
5. **UI / test-first 适用性** — 命中时读取对应参考文件，并在 prd.md 记录 `## UI Design` 或确认测试接缝。
6. **关键决策** — 只收影响范围、验收、风险、外部接口或不可逆成本的技术决策；纯内部实现选择推迟给 implement executor。
7. **边界情况、失败路径与被否决的备选** — 让 happy-path 验收不成立的路径。
8. **收敛确认** — frontier 清空后做最终核对。

## 第一轮问题批次

1. 这套需求里最不能妥协的一条是什么？如果只能交付一半，砍哪一半？
   - 我的建议：先保核心价值链路，砍增强型体验。理由：核心链路决定验收是否成立，增强项可后续迭代。
2. 哪些部分你已经认定"就是这样"，哪些其实还没想清楚？
   - 我的建议：把"认定"的部分直接作为决策记录进 prd.md，只把真正悬而未决的节点放进 frontier。理由：减少无效提问轮次。
3. 有没有一个用户场景，按现在的描述走完会得到错误结果？
   - 我的建议：优先枚举失败路径和边界输入，而不是先完善 happy path。理由：边界情况最容易让验收标准失真。

相关问题我会合并（答一题即答另一题的就并成一问），每个决策节点我都会给出带理由的推荐答案，你只需在"推荐默认值"和"明确备选"之间选择。
