## 先从 Goal 和价值锚定

"给移动客户端加离线缓存" 的核心价值通常是：**弱网/无网时核心功能可用、启动与浏览更快、减少重复请求省流量省电**。这三条的优先级不同，后面的所有取舍都会跟着变。所以我先确认目标，再一次性铺开当前所有需要拍板的决策点。

## 当前决策前沿（一次性列出，每条附我的推荐）

1. **目标与成功指标**：离线缓存首要解决什么——无网可用、加载提速，还是降服务器负载？
   - 推荐：以"无网时核心浏览路径可用"为主目标，指标定为"离线打开核心页面成功率 ≥ 95%"。理由：这是用户感知最强、验收最明确的目标；提速类收益可以随后用启动耗时量化。

2. **缓存范围**：缓存哪些内容——接口响应、静态资源、图片、还是整页快照？
   - 推荐：第一期只缓存核心列表+详情两类接口响应和已浏览图片。理由：覆盖面够用且失效逻辑简单；整页快照侵入性大，放到二期。

3. **存储方案**：用什么存——SQLite、文件系统、还是平台原生存储（iOS NSURLCache / Android OkHttp Cache）？
   - 推荐：HTTP 层用原生 URL 缓存，业务数据用 SQLite 单表存 JSON。理由：原生缓存白拿失效协商；SQLite 事务可靠、便于做容量淘汰。

4. **失效与新鲜度策略**：TTL、stale-while-revalidate，还是版本号主动失效？
   - 推荐：stale-while-revalidate + 每条资源独立 TTL（列表 5 分钟、详情 30 分钟）。理由：离线时立刻有内容可看，联网后后台刷新，体验与一致性兼顾。

5. **写一致性**：离线时的用户操作（点赞、收藏、草稿）怎么处理？
   - 推荐：第一期只读缓存，离线写操作直接置灰并提示"需联网"。理由：写队列+冲突合并是整个方案最复杂、最易出数据事故的部分，先明确不做。

6. **容量与淘汰**：缓存上限多少、超了怎么清？
   - 推荐：100MB 上限，LRU 淘汰，手动"清除缓存"入口放设置页。理由：移动端常规水位，LRU 实现简单且行为可预期。

7. **安全合规**：缓存是否含隐私数据、是否加密、登出是否清空？
   - 推荐：默认不缓存鉴权敏感接口；登出时全量清空。理由：先堵最高风险的泄露路径，加密等威胁建模确认后再加。

8. **验收边界**：第一期做到什么程度算完成？
   - 推荐：以"断网可浏览最近访问过的列表与详情"为验收标准，含单测覆盖缓存读写与淘汰路径。理由：范围收敛，测试先行可直接落实。
