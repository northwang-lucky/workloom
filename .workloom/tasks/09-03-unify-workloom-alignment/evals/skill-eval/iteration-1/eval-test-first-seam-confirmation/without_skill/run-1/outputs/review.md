## 为什么先解决 test-first 节点

重试逻辑天然带状态机语义（首次调用、退避、幂等键、熔断、最终失败上报），不在实现前锁定测试边界，Phase 2.1 很容易写成"实现先行、测试补票"，验收时就无法区分"测过了"和"恰好能跑"。所以我把 test-first 适用性作为本轮对齐的最后一个待决问题，确认后立即写回 PRD 验收标准，再进入评审与启动。

## 待确认问题（一次性批量提出）

我计划用 `ask_user_question` 把以下问题放在一个批次里问，避免多轮往返：

1. 是否要求本任务采用 test-first 交付？选项：
   - A. yes（推荐）：全部交付严格走红-绿循环，先写失败测试再写最小实现。
   - B. no：不强制 test-first，实现与测试顺序由实现者自定。
   - C. critical-paths-only：仅对关键路径（重试决策、退避计算、幂等去重、最终失败处理）强制 test-first，其余配套代码（配置、日志、脚手架）不强制。

2. 若选 yes 或 critical-paths-only，请确认关键路径的测试接缝（seams），即允许测试替换/旁路的协作边界。我基于通用重试架构给出推荐清单，请逐项确认或增删：
   - A. 下游支付网关调用客户端（推荐 seam：接口注入 + fake/mock，覆盖成功、可重试错误、不可重试错误、超时四类响应）。
   - B. 时钟与退避计时器（推荐 seam：注入 Clock/BackoffPolicy，测试里用虚拟时间驱动，避免真实 sleep）。
   - C. 重试状态持久化存储（推荐 seam：仓储接口 + 内存实现，验证中断恢复与重复提交去重）。
   - D. 消息/事件出口（推荐 seam：事件发布接口 + 内存收集器，断言最终成功/失败事件恰好一次）。

## 我的推荐

推荐第 1 题选 A（yes）。理由：重试服务缺陷代价高（重复扣款、丢失终态），且 seams 清晰、fake 成本低，test-first 的收益明显高于额外开销。若担心非核心代码拖慢节奏，C 也是可接受的折中，但需要在 PRD 里把"关键路径"枚举成上面 2 中的具体行为，避免执行时口径漂移。
